# Анализ: R-07 crossover-гейт на бенчмарке №2 (task-dependence vs global bias)

**Дата:** 2026-08-16 · **Статус:** закрывает `todo://arbiter/r-07-crossover-gate`
**Основание:** TODO `r-07-crossover-gate` — «Crossover-гейт (task-dependence, а не
global bias) на бенчмарке №2», триггер «второй task_type с rank_score в
`benchmark_runs`». Блокер `atp-platform#second-task-type-sweep` снят: свип второго
task_type выполнен на стороне atp-platform (issue atp-platform#279 закрыт),
payload'ы доставлены контрактным путём через `report_benchmark`.

## 1. Вопрос гейта

R-07 Phase 1 одним бенчмарком (`code-review`) доказал **механизм**: проводка
`report_benchmark → benchmark_runs → get_benchmark_score → apply_benchmark_rerank`
работает, магнитуда сигнала реальна. Он не доказал **направление**: является ли
`rank_score` task-зависимым сигналом (и тогда скоупинг по `task_type` оправдан)
или это глобальный bias одного бенчмарка, который скоупинг лишь маскирует.

## 2. Данные

Эффективные скоры по семантике `get_benchmark_score` (последний прогон по `ts`
на пару agent×benchmark, `rank_score` из `score_components` приоритетнее
скалярного `score`, кламп в `[0, 1]`):

| agent_id | `code-review` | `req-extraction` |
|---|---|---|
| `opencode@glm-5.1` | **0.915** | 1.0 |
| `codex_cli@gpt-5.5` | 0.781 | 1.0 |
| `claude_code@claude-sonnet-4-6` | 0.705 | 1.0 |

- `code-review`: 18 прогонов (2026-06-21…07-03), разброс по трём верхним агентам
  Δ = 0.209.
- `req-extraction`: 3 прогона от 2026-08-16, `run_id`
  `bd382836-3ed8-43e5-ae27-6df07a8a972f` (claude_code),
  `5c96dd28-03e4-402e-a916-8e4197769b21` (codex_cli),
  `81fe74a4-07b2-4f2f-9ea5-c1a587eb9727` (opencode); у всех `rank_score = 1.0`.

## 3. Вывод по вопросу гейта

**Сигнал task-зависим; глобального bias не наблюдается.** Преимущество
`opencode@glm-5.1` в +0.21 на `code-review` не переносится на `req-extraction`
константным сдвигом — на втором суите оно исчезает полностью (ничья 1.0/1.0/1.0).
Это ровно тот случай, от которого защищает дизайн: `benchmark_id_for` скоупит
скор по task_type, поэтому «сильный на code-review» агент не получает незаслуженную
дельту на чужом типе задач.

Поведение тайбрейкера на ничьей честное и гарантировано математически: аддитивная
дельта `(score − 0.5) × weight` одинакова для всех участников с равным скором,
равномерный сдвиг не меняет порядок, остаточная ничья разрешается детерминированным
tie-break по `agent_id` (введён `cb71b57`, #26). Re-rank на таком суите — no-op
среди оценённых агентов, а не ложный переворот.

### Оговорка: потолок суита (важно для честности)

`req-extraction` **сатурирован**: все три агента упёрлись в 1.0
(`mean_run_pass_rate` ≥ 0.98). Сатурированный суит доказывает *отсутствие переноса
bias*, но принципиально не может показать **crossover в сильной форме** (переворот
ранжирования: A > B на T1, B > A на T2) — на нём никто никого не ранжирует.
Сильная форма остаётся ненаблюдённой и уезжает контекстом в развилку
`r-07-link-strength-decision`, а не остаётся отдельным гейтом: для решения о силе
связи достаточно уже имеющегося факта (см. §4).

## 4. Следствие для развилки `r-07-link-strength-decision`

Данные добавляют аргумент в развилку «(а) сильнее связать `rank_score` с
confidence vs (б) переобучить дерево на мягкие листья»: **усиление веса
(`ARBITER_BENCH_WEIGHT`) ничего не даёт на суитах-ничьих** — разброс существует
только там, где задача реально дифференцирует агентов. Умножение нулевого спреда
на больший вес остаётся нулём; выигрыш возможен только на дискриминативных суитах,
где и текущий вес уже работает как тайбрейкер. Сама развилка — отдельный пункт,
здесь не решается.

## 5. Что сознательно НЕ делаем

- **Не расширяем `benchmark_id_for`** маппингом на `req-extraction`: ни один
  `TaskType` (Feature/Bugfix/Refactor/Test/Docs/Review/Research) не является его
  потребителем в роутинге, а расширение без потребителя противоречит политике
  «не расширять API без запроса» (TODO «Не делаем»). Когда потребитель появится,
  это one-liner в `route_task.rs` + строки в `benchmark_runs` — «no other code
  change is required» (комментарий у `benchmark_id_for`).
- **Не заводим гейт на «бенчмарк №3»**: открытый вопрос сильной формы crossover
  зафиксирован как контекст развилки, новый блокер под него не нужен —
  дискриминативность будущих суитов задаёт atp-platform, не arbiter.
